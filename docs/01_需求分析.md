# CampusEvent 需求分析（初始版本 baseline-v1）

> 依据：《软件工程》实验指导书 3.2 节、3.5 节与附录 B；项目代号 CampusEvent。
>
> 版本：`baseline-v1`。需求变更单（CR）尚未发布，本文不包含任何变更后的需求；变更阶段材料见 `docs/04_变更影响分析_模板.md`。

## 1. 目的与产品范围

校园管理员发布活动，学生浏览活动并报名。初始版本支持两类报名规则：

- **直接报名**：名额充足时立即通过，否则报名失败。
- **审核型报名**：学生提交后进入“待审核”，由管理员批准或拒绝；批准时再次检查名额。

报名与审核结果通过**站内消息**通知学生。

范围内：活动管理、活动浏览与按名称筛选、报名与取消、两类报名规则、审批、状态管理、站内通知、按活动统计、SQLite 持久化。

范围外：账号注册、多用户权限体系、候补队列、邮件/短信通知、活动签到、分页、移动端 App、第三方日历、真实支付。

## 2. 角色与权限

| 角色 | 账号来源 | 权限 |
|---|---|---|
| 学生 Student | `student` 表 | 浏览活动、报名、取消自己的报名、查看自己的消息 |
| 管理员 Admin | 配置中的固定演示账号 | 创建/编辑/删除活动、查看报名、批准/拒绝待审核报名、查看统计 |

- 学生不能进入管理端；管理员不能以学生身份报名。
- 不实现注册与找回密码；演示账号见 README。
- 权限校验在路由层（会话角色）和服务层（报名归属）双重执行。

### 3.2 关键用例

#### UC-04 报名

- **前置条件**：学生已登录；活动存在；当前时间早于活动开始时间；该学生没有该活动的有效报名（待审核或已通过）。
- **主流程**：
  1. 学生打开活动详情，点击“报名”。
  2. 系统读取活动与当前已通过人数。
  3. 系统按 `policy_type` 选择报名策略。
  4. 直接报名：名额充足则创建“已通过”报名；否则返回“名额已满”。
  5. 审核型报名：创建“待审核”报名。
  6. 事务提交后写入站内消息。
  7. 页面显示结果，统计同步更新。
- **异常/分支**：
  - 活动不存在：404。
  - 活动已开始：拒绝新增报名。
  - 已有有效报名：拒绝重复报名，提示当前状态。
  - 直接报名满额：不创建报名记录，提示“名额已满”。
  - 通知写入失败：报名仍成功，失败写入 `notification_attempt`，页面不谎报通知成功。
- **后置条件**：成功时新增一条报名记录；直接报名为“已通过”，审核型为“待审核”；消息列表新增站内消息。

#### UC-05 取消报名

- **前置条件**：学生已登录；报名属于本人；状态为“待审核”或“已通过”。
- **主流程**：进入“我的报名”或活动详情，点击取消；系统将状态改为“已取消”；统计中的已通过数/剩余名额同步变化。
- **异常**：报名不存在或不属于本人 → 403/404；状态已取消/已拒绝 → 提示不可重复取消。
- **后置条件**：记录保留历史，不物理删除；学生可再次报名（新记录）。

#### UC-06 审批报名

- **前置条件**：管理员已登录；报名为“待审核”；活动尚未开始（批准时）。
- **主流程（批准）**：打开活动审批页 → 选择待审核记录 → 点击批准 → 系统复查名额 → 有名额则改为“已通过”并通知；无名额则提示失败，记录保持“待审核”。
- **主流程（拒绝）**：点击拒绝 → 状态改为“已拒绝”并通知。
- **异常**：非待审核状态；活动已开始；名额已满；并发下记录已被处理。
- **后置条件**：状态与通知一致；不会超过人数上限。

#### UC-07 管理活动

- **新建**：必填名称、类型、开始时间（未来）、地点、容量（正整数）、报名方式。
- **编辑**：容量不得低于当前已通过数；存在有效报名时不允许修改报名方式；开始时间的新值必须为未来。
- **删除**：存在任何报名记录时拒绝删除并提示；否则删除。
- **异常**：非法输入、活动不存在、容量冲突、报名方式冲突。

## 4. 业务规则

| 编号 | 规则 |
|---|---|
| BR-01 | 活动容量为正整数；已通过报名数不得超过容量。 |
| BR-02 | 直接报名：名额充足时创建“已通过”；满额时不创建记录。 |
| BR-03 | 审核型报名：提交后为“待审核”；待审核不占名额。 |
| BR-04 | 批准时必须再次检查名额；满额时批准失败，记录保持“待审核”。 |
| BR-05 | 同一学生对同一活动最多一条有效报名（待审核/已通过）；已取消/已拒绝保留历史，允许再次申请。 |
| BR-06 | 学生只能取消自己的待审核/已通过报名；活动开始后不允许新增报名，取消不受开始时间限制。 |
| BR-07 | 管理员批准必须发生在活动开始前；拒绝可在活动开始后用于清理遗留待审核记录。 |
| BR-08 | 管理员删除有报名记录的活动必须被拒绝；无报名记录才可删除。 |
| BR-09 | 报名/审核动作产生站内消息；通知失败留痕，但不得回滚已提交的报名。 |
| BR-10 | 统计口径：已通过数只计 `APPROVED`；待审核数只计 `PENDING`；剩余名额 = max(0, 容量 − 已通过数)。 |

## 7. 非功能需求

| 类别 | 要求 | 验证方式 |
|---|---|---|
| 性能 | 200 条活动规模下页面响应 < 2 秒 | 本地手工/验收记录 |
| 可靠性 | 重启后活动、报名、消息不丢失 | C10、`test_persistence.py` |
| 事务一致性 | 并发报名不超容量；重复有效报名被数据库约束兜底 | 部分唯一索引、`BEGIN IMMEDIATE`、单测 |
| 通知可靠性 | 失败留痕，不影响报名 | 注入失败观察者测试 |
| 安全 | 密码哈希、会话登录、参数化 SQL、Jinja 自动转义 | 代码审查 + 单测 |
| 可用性 | 中文界面、错误提示清晰、危险操作二次确认 | 页面验收 |
| 可维护性 | 分层、策略/观察者解耦、文档与代码一致 | 设计评审 |
| 兼容性 | 常见桌面浏览器；Python 3.11+ | 手工验证 |

已知安全限制：课程演示版没有 CSRF token；管理员为固定演示账号；公网只放虚构数据。生产化前需补 CSRF、改密、限流与审计。

## 8. 初始验收用例

| 编号 | 输入/操作 | 预期结果 |
|---|---|---|
| C1 | 管理员创建直接报名活动，容量 2 | 创建成功，可供学生报名 |
| C2 | 学生 A 报名直接报名活动 | 直接变为“已通过”并通知 |
| C3 | 学生 A 再次提交相同活动报名 | 拒绝重复有效报名 |
| C4 | 学生 B 报名同一活动，名额已满后学生 C 再报名 | B 通过，C 因名额不足失败 |
| C5 | 创建审核型活动，学生 A 申请 | 状态为“待审核” |
| C6 | 管理员批准 A 的待审核报名 | 变为“已通过”且生成通知 |
| C7 | 管理员拒绝另一待审核报名 | 变为“已拒绝”且生成通知 |
| C8 | 批准操作时容量已满 | 批准失败，不超出人数上限 |
| C9 | 学生取消待审核或已通过报名 | 状态“已取消”，统计同步变化 |
| C10 | 重新启动服务，查询活动、报名、通知 | 数据仍一致 |

## 9. 范围外与不实现项

- 候补队列、邮件/短信、活动签到、二维码、支付。
- 学生注册、找回密码、多管理员、细粒度权限。
- 活动分页、复杂组合筛选、日历视图。
- 真实消息推送、后台定时任务。
- 需求变更（CR）相关功能：**等待教师统一发布后另行实施**。
