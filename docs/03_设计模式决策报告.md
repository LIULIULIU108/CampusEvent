# CampusEvent 设计模式决策报告

> 版本：`baseline-v1`。本文说明为什么在初始版本引入策略、注册表、观察者与仓储模式，以及它们带来的成本和后续变更空间。CR 未发布，因此不包含变更后的实现结论。

## 1. 变化点识别

从需求中可识别出四个变化方向：

| 变化方向 | 当前实现 | 未来可能的变化 |
|---|---|---|
| 报名规则 | 直接报名、审核报名 | 候补、邀请制、限额分组等 |
| 通知机制 | 站内消息 | 邮件、短信、企业微信等 |
| 持久化 | SQLite | 其他数据库/云存储 |
| 页面/交互 | 服务端渲染 | 前后端分离、移动端 |

初始版本只对**已经存在两类实现**的报名规则和**已经存在业务事件**的通知做抽象；不为尚未出现的变化预写代码。

## 2. 策略模式：报名规则

### 2.1 问题

如果 `RegistrationService` 直接写：

```python
if activity.policy_type == "DIRECT":
    if remaining > 0: status = "APPROVED"
    else: raise ...
elif activity.policy_type == "APPROVAL":
    status = "PENDING"
```

则每新增一种规则都要修改核心服务，且名额检查时机与规则类型耦合，测试需要重复覆盖分支。

### 2.2 方案

- `RegistrationPolicy` 接口：`decide(context) -> PolicyDecision`。
- `DirectRegistrationPolicy`：名额充足→`APPROVED`；否则拒绝（不落库）。
- `ApprovalRegistrationPolicy`：→`PENDING`，名额在审批时检查。
- `PolicyRegistry`：按 `PolicyType` 取实现；未知类型显式报错。
- `CapacityChecker`：统一计算剩余名额，注入直接报名策略与审批服务。

### 2.3 备选方案与取舍

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| if/elif 分支 | 代码少、直观 | 新增规则改核心类；名额时机难统一；测试分支膨胀 | 拒绝 |
| 状态模式 | 适合状态驱动行为 | 这里的状态变化由规则和审批共同触发，状态类会过多 | 过重 |
| 策略 + 注册表 | 新增规则只加类/注册；主流程稳定；可单测 | 类数量增加、调用链变长 | **采用** |

### 2.4 成本

- 新增 4 个类/接口（策略接口、两个实现、注册表）和 1 个协作者（CapacityChecker）。
- 阅读代码需要先理解上下文对象与决策对象；对初学者不如 if/else 直观。
- 收益：直接/审核两种规则的差异被隔离，服务层只依赖抽象；后续新增规则的影响面可预测。

## 3. 注册表/简单工厂：策略选择

- `PolicyRegistry` 在应用启动时构造 `{PolicyType.DIRECT: DirectPolicy(...), PolicyType.APPROVAL: ApprovalPolicy(...)}`。
- `resolve()` 对未知类型抛 `UnsupportedPolicyError`，避免静默落到某个默认策略。
- 选择注册表而非在每个服务里 `if`：策略选择集中在一处，新增规则只改注册表一行。
- 代价：注册表需要与枚举/数据库约束保持同步；启动时缺少注册会在测试中暴露。

## 4. 观察者/事件分发：通知机制

### 4.1 问题

报名成功后需要写站内消息。如果 `RegistrationService` 直接调用 `MessageRepository`：

- 报名事务与通知写入耦合；通知失败可能回滚报名，或需要复杂的嵌套事务。
- 新增通知渠道要改报名服务。
- 重复发布容易产生重复消息。

### 4.2 方案

- `DomainEvent`：事件 ID、类型、活动/学生/报名 ID、发生时间、上下文。
- `EventPublisher`：业务事务提交后分发；逐个观察者隔离失败。
- `NotificationObserver`：`handle(event, conn)`。
- `InAppNotificationObserver`：写 `message`。
- `notification_attempt`：`(event_id, channel)` 唯一，记录 PENDING/SENT/FAILED；重复事件直接跳过。

### 4.3 备选方案与取舍

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 服务内直接写消息 | 简单、同事务 | 业务与通知耦合；渠道扩展改服务；失败语义混乱 | 拒绝 |
| 消息队列 | 解耦彻底、可重试 | 课程项目引入中间件，超出边界；运维复杂 | 过度设计 |
| 观察者 + 事后发布 | 解耦、易扩展、失败可留痕 | 通知不是强一致；需要幂等表 | **采用** |

### 4.4 事务边界与失败语义

- 报名/审批先提交，再发布事件；通知失败不回滚报名。
- 观察者失败写入 `notification_attempt`，页面不宣称通知成功。
- 初始版本不自动重试；后续可通过同一张表做重试或新增渠道。
- 代价：通知是 best-effort，存在“报名成功但通知未送达”的窗口；通过留痕和页面提示降低风险。

## 5. 仓储模式：持久化隔离

- 每个聚合根一个 Repository：Student/Activity/Registration/Message/NotificationAttempt。
- Service 不写 SQL；Repository 返回 dataclass，不泄露 `sqlite3.Row`。
- 收益：测试可用临时 DB；未来换存储只改仓储；SQL 集中审查。
- 代价：简单查询也要经过一层；对极小项目略显冗长。本项目需要清晰展示分层，故保留。

## 6. 模式协作

```text
Web → RegistrationService
        ├─ PolicyRegistry → RegistrationPolicy（Direct/Approval）
        ├─ CapacityChecker（策略/审批共享）
        ├─ RegistrationRepository
        └─ EventPublisher → NotificationObserver → MessageRepository
                              └─ NotificationAttemptRepository（幂等/失败留痕）
```

依赖方向：Service 依赖抽象；Domain 不依赖 Flask/SQLite；通知不反向依赖报名服务。

## 7. 成本与收益总结

| 维度 | 引入模式前 | 引入模式后 |
|---|---|---|
| 新增报名规则 | 改服务分支 | 新增策略实现 + 注册 |
| 新增通知渠道 | 改报名服务 | 新增观察者 + 注册 |
| 单测 | 服务测试覆盖所有分支 | 策略/观察者独立单测 + 服务集成测试 |
| 代码量 | 少 | 多约 5—7 个类 |
| 调试 | 调用链短 | 多一层间接，需要看事件/尝试表 |

结论：本项目的变化点（两类报名、通知解耦）真实存在，模式收益大于成本；但不应把模式当作目标——若只有一种报名规则，直接实现更合适。

## 8. 面向未来 CR 的评估（不实现）

若后续 CR 属于以下类型，预期影响面如下（仅设计推演，不是实际变更结果）：

| CR 类型 | 预期新增/修改 | 说明 |
|---|---|---|
| 新增报名规则 | 新增策略类 + 注册表一行 + 枚举/迁移 + 测试 | 主流程理论上不改；需评估名额语义 |
| 新增通知渠道 | 新增观察者 + 组装注册 + 渠道配置/迁移 | 事件发布器不改；需评估失败与重复 |
| 修改通知内容 | 改文案构建器 + 测试 | 影响面小 |
| 修改名额规则 | 改 CapacityChecker/策略 + 测试 | 需回归 C1—C10 |

> 以上为设计扩展点说明，**不是已完成的变更影响分析**。教师 CR 发布后，按 `docs/04_变更影响分析_模板.md` 填写实际受影响类、风险、测试与工时，并从 `baseline-v1` 建分支实施。
