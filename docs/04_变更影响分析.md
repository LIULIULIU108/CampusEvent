# CampusEvent 需求变更影响分析（CR-01 + CR-02）

> 变更来源：教师材料《实验二教师专用材料》中的 CR-01、CR-02。
>
> 基线：Git 标签 `baseline-v1`；变更分支：`change-v2`。**原 `app/`、`tests/`、`run.py`、`cli.py` 保持 baseline 原样；本变更全部实现于 `app_v2/`、`tests_v2/`、`run_v2.py`、`cli_v2.py`。** 本文是实施前的设计分析，实施结果与回归数据见第 7、8 节及 `docs/05_测试报告.md`。

## 1. 变更摘要

| 变更 | 内容 | 验收 |
| --- | --- | --- |
| CR-01 | 新增“年级限定直接报名”规则：Student 增加 `grade`（1—4）；仅大二、大三（grade ∈ {2,3}）可报名；其他年级明确拒绝；仍遵守名额、开始时间、重复报名约束；原直接/审核行为不变 | CR1-01—CR1-05 |

## 3. 设计决策

### 3.1 CR-01：新增独立策略，而不是修改报名主流程

选择新增 `GradeLimitedDirectRegistrationPolicy`：

- 年级限制属于“报名规则”，与直接/审核规则并列；`RegistrationService` 只做活动存在、未开始、无有效报名等公共校验。
- 策略内部先判断年级，再调用 `CapacityChecker` 判断名额；不满足年级时返回明确原因。
- 原 `DirectRegistrationPolicy`、`ApprovalRegistrationPolicy` 不动，C1—C10 行为保持不变。
- 代价：策略数量从 2 增到 3，注册表增加一行；收益：主流程零修改，规则可独立单测。

备选“在服务里加年级 if”被拒绝：会让核心服务随规则类型膨胀，且难以说明公共约束与策略责任的边界。

### 3.2 CR-02：新增观察者，而不是在报名服务里发邮件

- `EmailNotificationObserver` 与 `InAppNotificationObserver` 并列订阅同一 `DomainEvent`。
- `supports()` 只对“报名通过 / 审核通过 / 审核拒绝”返回真；待审核提交不发邮件，避免无意义通知。
- `email_outbox.event_id` 唯一；`notification_attempt(event_id, channel)` 继续做渠道级幂等。
- 发送失败时 `on_error()` 写 `email_outbox=FAILED`，`notification_attempt=FAILED`；业务事务已提交，不回滚报名。
- 代价：`EventPublisher` 增加两个钩子，通知子系统更复杂；收益：站内/邮件可独立失败、独立观测，后续可替换真实 SMTP 或新增渠道。

### 3.3 数据库迁移

- SQLite 不能直接改 CHECK，因此 v1→v2 重建 `student`、`activity`，关闭外键后复制数据、重建表、恢复外键，并修正 `sqlite_sequence`。
- 迁移只执行一次（`PRAGMA user_version 1→2`）；新库直接按 v2 建表。
- 迁移测试验证学生、活动、报名、消息保留，外键检查通过，新策略可写入。

## 4. 风险与应对

| 风险 | 应对 |
| --- | --- |
| 重建表导致数据/外键丢失 | 事务内重建；`PRAGMA foreign_key_check`；迁移测试保留 v1 数据 |
| 新策略改变原有行为 | 原策略零修改；C1—C10 回归 |
| 邮件失败影响报名 | 提交后发布；失败写 outbox/attempt，不回滚 |
| 同一事件重复发邮件 | event_id 唯一 + notification_attempt 幂等 |
| 旧库学生 grade 默认 1 | 迁移默认 1；演示库用 `set-demo-grades` 同步 2/3/1/4 |
| 公网迁移/部署失败 | 先本地迁移测试，再远端执行；保留 baseline 标签 |

## 8. 实施与回归结果

- 全量 pytest：**123 passed**（2026-11-26，本地）。
- CR1-01—CR1-04、CR2-01—CR2-04、MIG-01 均通过。
- C1—C10 回归：**10/10 通过**（pytest 与真实 HTTP 验收）。
- 公网 change-v2 部署与截图见 `docs/05_测试报告.md`、`docs/07_部署文档.md`。
- 设计成本：新增 7 个类/异常与一个迁移文件；`EventPublisher` 多两个钩子。收益：核心报名/审批服务零修改，邮件渠道可独立失败/观测，后续换真实 SMTP 或加渠道时影响面可控。

## 9. 结论

CR-01 通过“新增策略”实现，CR-02 通过“新增观察者 + 发件箱”实现；两者都遵守原公共约束，C1—C10 回归无失败。变更增加了策略/通知基础设施复杂度，但没有修改报名/审批核心流程，符合本项目的设计边界。以上数据为实际测试结果，未虚构变更指标。
